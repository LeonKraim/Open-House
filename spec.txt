Implementation plan

Phases are in order, each with an exit criterion. No dates or durations.

You have 4 reference repos in your resources folder, and ccostan's is one of them. 
Tech stack
Layer	Choice	Why
Engine core	Python 3.12+, pure (no homeassistant imports), async, Pydantic v2 models	Same language as HA, and models give validation plus JSON Schema for free
Schemas	JSON Schema generated from Pydantic, versioned	One source of truth for engine, panel, pack CI, and AI tools
Pack format	YAML (safe loader), validated against the schema	Human-readable and declarative-only
HA integration	Custom integration using config flow, subentries, Repairs, diagnostics, panel_custom, and websocket API, distributed via HACS	The native way to get a sidebar tab and setup flow
Panel	TypeScript + Lit web components, built with Vite, types generated from the JSON Schemas	Matches HA's own frontend stack and the hass object
Simulator	Pure-Python FakeHouseAdapter with a virtual clock	Fast, deterministic, no HA boot
AI control surface	Python library, CLI (Typer), and MCP server (official MCP Python SDK)	Lets an agent drive everything
Unit and scenario tests	pytest, pytest-asyncio, YAML scenario DSL	The bulk of coverage
Property and mutation tests	Hypothesis, mutmut	Invariants and test-quality checks
HA integration tests	pytest-homeassistant-custom-component	Deepest HA fixtures available
E2E and UI	Docker HA container seeded with virtual entities, driven over websocket, plus Playwright	Real-instance confidence
Quality	ruff, pyright (or mypy), pre-commit, ESLint and tsc for the panel	Strict typing keeps AI-written code honest
CI/CD	GitHub Actions, GitHub Pages for the registry index	No backend needed at first
Signing	Sigstore/cosign for release artifacts, SHA-256 pinning for packs	Verifiable trust tiers
Registry	Separate Git repo of pointer files plus generated index.json and revoked.json	Homebrew/HACS-style, PR-based publishing
Docs	MkDocs Material	Fast user and pack-author guides

Verify current versions and APIs of HA (subentries, panels, dashboard strategies) and the MCP SDK before pinning anything.

Phase 0: Foundations
0a: Reference repo research (all 4 repos in the resources folder)
Identify and record each repo: name, author, purpose, HA style (YAML packages, blueprints, custom integration, dashboards), and what it's best at.
License and attribution, per repo: read each license, decide what can be reused or adapted, and record attribution requirements. Nothing is copied until each one is settled. If a license is unclear, ask the author.
Full inventory, per repo: every package, automation, script, helper, template sensor, blueprint, dashboard, and custom integration.
Behavior extraction: for each one, record what it does, its triggers, conditions, and actions, and the slots it would need. Classify as generic (default room behavior), module candidate (pack), or personal/hardware-specific (discard).
Cross-repo comparison: find behaviors that appear in more than one repo, compare how each repo solves them, and pick the best approach or merge them. Overlap across repos is the strongest signal that something belongs in the defaults.
Hardcoding audit: every hardcoded entity ID, name, or location, since each becomes a slot. Compare naming conventions across repos so the slot vocabulary isn't biased toward one author.
Room-type mapping: derive default room types and slot sets from the real rooms across all four setups.
Edge cases they already solved: flaky devices, restarts, false triggers, notification spam. Each becomes a simulator scenario.
Pain points: where each setup is brittle or hard for a newcomer to replicate, which defines what yours must do better.
Dependency list: HACS integrations and add-ons each repo relies on, and whether to require, replace, or avoid each.
Deliverable: one merged behavior catalog (behavior, source repo(s), required slots, optional slots, category, reuse status, license).
0b: Schemas and repo
Freeze versioned schemas for room types and slots (derived from the catalog), pack manifests, the trigger/condition/action vocabulary, modes, profiles, and the export document.
Repo layout: engine/, ha_adapter/, custom_components/, panel/, packs/official/, sim/, and a separate registry/ repo.
CI, linting, typing, and pre-commit set up.
Exit: every piece of all four repos is classified, the slot vocabulary comes from real usage across them, and a hand-written example house and pack validate against the schemas.
Phase 1: Engine and full mock house
HouseAdapter interface plus FakeHouseAdapter. Every entity is a mock and everything is controllable: add/remove entities, set state, manual user actions, unavailable devices, injected faults, restarts.
Virtual clock, seeded randomness, no network, snapshot/restore.
Engine core: slot binding (optional, list-capable), layered config resolver, house modes, arbitration and priorities, manual-override detection, rate limits, and a decision log that doubles as the test oracle.
First behaviors: motion lighting (lux, then sun fallback), override, away shutdown.
Scenario runner with YAML DSL, Hypothesis invariants, mutation testing, and JSON failure output.
Fixture houses: minimal, messy (duplicates, unavailable devices), 150+ devices, no lux sensors.
CLI, library, and MCP server (advance_time, set_state, user_action, inject_fault, snapshot/restore, get_decision_log, install_pack, export_config, import_config).
Exit: an AI agent can build a house, run scenarios, read the log, and iterate with no HA installed.
Phase 2: Pack system
Declarative-only interpreter with a capability sandbox: only bound entities, only declared services, a banned-service list, and red-flagged dangerous permissions.
Dependencies, conflicts, engine_api ranges, semver, SPDX license, i18n strings.
Pack kinds: module, room-template, behavior, profile-set, house-template.
Official packs: Bedtime button (lights off, Sleep mode, optional thermostat, locks off by default), Roomba button (idle starts, cleaning sends home, paused resumes, stuck notifies), bathroom fan, guest mode, default room templates, plus packs derived from the merged catalog.
Triggers from a dashboard button or a physical button.
Pack CLI: validate, test, diff-permissions.
Exit: official packs pass validation and scenarios, and two modules cannot fight over one light.
Phase 3: Profiles, export, migrations
Multiple profiles per room as deltas over the room base. Layers: pack defaults, house, room, active profile, temporary override.
Simultaneous profiles through real axis support (for example Lighting and Climate at once).
House-level profiles that bundle room-profile selections (for example "Vacation", "Guests over"), exportable and shareable as packs.
Activation rules by manual pick, schedule, house mode, or trigger, with hysteresis, minimum dwell, and cycle detection.
Export/import: full backup, plus a scrubbed shareable template that is itself a pack. Bindings store registry UUID plus entity_id. Import runs a dry-run diff, a re-link wizard, and an automatic snapshot with undo.
Schema migrations tested against golden old exports.
Exit: export then import is identity (property test), and old fixtures migrate.
Phase 4: HA integration (HAOS)
HAAdapter with contract tests against both adapters so the fake stays honest.
First-run config flow: confirm areas, pick room types, auto-guess bindings, choose people for away detection, plain-language review, Activate. A simple setup needs nothing more.
HA Areas are the source of truth for rooms; rooms are subentries where supported.
Per-room entities: mode, profile select, occupied, auto-lighting switch.
Repairs, diagnostics, startup safety (unavailable is not off), and coexistence with existing user automations.
Exit: a fresh HA install reaches working automation through the setup flow alone.
Phase 5: Own sidebar tab
Custom panel, admin-only, backed by a websocket API for all CRUD.
Tabs: Overview, Rooms, Modules, Profiles, Store, Activity, Health, Import/Export.
Per-room settings page lists every bound device with status and rebind/replace actions, and shows only high-level options, rendered from pack schemas with no pack-supplied JS.
"Add module to room" shows only packs the room can satisfy, with a conflict check before install.
Limited view for non-admin household members, plus a generated dashboard.
Exit: the whole journey runs with no YAML.
Phase 6: removed
Apple Home and the HomeKit bridge are out of this project's scope. The phase number is kept rather than reused, so existing references to phases 7 and 8 keep their meaning.
Eject -- "eject room to plain automations" plus clean uninstall -- is deferred, not cancelled.
It is in no phase, and is a candidate to add after phase 8 only if the user approves it first.
Phase 7: Registry and community store
Pointer files (repo, commit SHA, SHA-256, tier), generated index, revocation list.
CI: schema, permission lint, permission diff versus the previous version, scenario tests on the fake house, typosquat checks.
Tiers: Official (signed), Verified (human review), Community (no dangerous permissions), Local (from /config, warning banner, own install flow).
Store tab: browse, install by hash, update gating on permission changes, cached offline index, abandoned-pack flags.
Publish button: export as a template, then open a prefilled PR.
Exit: a third party publishes and installs a pack end to end.
Phase 8: Polish and hardening
Simulated user journey as automated e2e acceptance tests: setup, first-day override, bed button, Roomba, sensor death and replace, update with opt-in behaviors.
Messy-house fixtures, fault and fuzz passes, Docker e2e and Playwright on a schedule, and a real-home beta.
Safety audit: smoke/CO and leak alerts bypass all modes, nothing auto-unlocks or opens garages, sensor-death fallbacks.
UX: empty states, plain-language errors, decision log as "why did this happen," onboarding, What's new (opt-in), accessibility, mobile, localization.
Docs: user guide, pack author guide, security policy, and attribution for anything adapted from the reference repos.
